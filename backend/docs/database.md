# PostgreSQL: роли, схема и транзакции

`infra/postgres/001-roles.sql` выполняется администратором на новом томе образа
PostgreSQL. Это psql-скрипт с `\getenv` и `\gexec`, а не Flyway-миграция.
Пароли читаются из окружения и экранируются psql как SQL literals; не передаются
аргументами командной строки. Для существующего тома без ролей есть команда в README.
Автоматического удаления томов, пересоздания ролей и смены паролей нет.

`finance_migrator` владеет схемой app, таблицами и историей Flyway. Runtime имеет
USAGE схемы и явные права на данные, но не CREATE, TRUNCATE, BYPASSRLS, superuser
или членство в migrator. От PUBLIC отозваны права на БД и public schema;
runtime не может создавать даже временные таблицы. Flyway clean отключён.
Схема должна быть подготовлена до старта приложения: create-schemas=false.

V1 создаёт 10 таблиц без пользователей и стартовых категорий; V2 добавляет
registration_invites/devices, JWT families/jti, status, cascade и отзыв DISABLED.
Изменённая auth-схема проверяется как с нуля, так и upgrade с заполненной V1. Семь финансовых
и sync-таблиц имеют ENABLE/FORCE RLS с одинаковыми USING/WITH CHECK на user_id.
Auth-таблицы доступны runtime без RLS только для auth-слоя согласно ТЗ.
V3 добавляет email_verified_at/account_tokens и отзывает прежние семьи. V4 добавляет
recovery_state, отметку устройства и sync_recoveries с FORCE RLS (всего восемь таблиц с RLS).
Runtime читает epoch, но не может менять её или выполнять admin recovery-функции.
Миграции после применения не редактируются: дальнейшие изменения — новыми версиями.
Повторный старт не запускает повторное сидирование. Sync-журналы доступны runtime
только для INSERT/SELECT: история и tombstones не удаляются и не переписываются.

Порядок работы финансовых сервисов:

1. Проверить токен и получить UUID из серверного principal (реализовано).
2. Открыть транзакцию Spring: SyncService использует TransactionTemplate на одну операцию.
3. Вызвать `UserTransactionContext.setUser(verifiedUserId)` ровно один раз,
   до первого пользовательского SQL. Helper требует активную транзакцию именно
   своего datasource и устанавливает параметризованный set_config(..., true).
4. Выполнить JdbcTemplate-запросы с явными user_id-фильтрами на том же datasource.
   RLS дополняет эти фильтры. Commit/rollback сбрасывает контекст в PostgreSQL.

При регистрации в одной транзакции создаётся users, устанавливается новый серверный
UUID, затем создаются user_sync_state, персональные категории и sync_changes.
Тест подтверждает rollback всей этой последовательности при ошибке ограничения.
HTTP-сценарий регистрации реализован и проверен в AuthApiTest.

Propagation REQUIRED присоединяется к контексту внешнего сервиса: вложенные
репозитории не устанавливают его повторно. REQUIRES_NEW получает отдельное соединение
и должен установить свой контекст; после завершения восстанавливается внешний.
Пул должен иметь достаточно соединений для вложенных REQUIRES_NEW. Read-only
транзакции также устанавливают контекст. NESTED/savepoint не используется как граница
смены пользователя. Смешивание аккаунтов в одной транзакции запрещено helper-ом.

RLS защищает от забытых WHERE, но runtime технически может задать произвольный
custom setting. Поэтому UUID нельзя брать из HTTP-параметров или X-User-Id,
а запросы должны быть параметризованными. Auth-репозитории не должны возвращать
произвольные профили через внешний API. Эти ограничения проверены auth/sync API-тестами.

Деньги — BIGINT в минимальных единицах, даты расходов — DATE. Версии положительные,
лимиты и расходы >0. Категории связываются составным FK (user_id, category_id).
Схема допускает одинаковые UUID и названия у разных аккаунтов. Ключ идемпотентности
составной, sequence принадлежит аккаунту; глобального sequence нет. SHA-256 хранится
как 64 строчных hex-символа. Правила нормализации email/категорий, запрет активного
использования архивной категории и смены валюты после первого расхода относятся
к следующим этапам auth/domain, а не выдаются за реализованные CHECK-ограничения.

Источники: [PostgreSQL 18 RLS](https://www.postgresql.org/docs/18/ddl-rowsecurity.html),
[транзакционные JDBC-соединения Spring](https://docs.spring.io/spring-framework/reference/data-access/jdbc/connections.html).


V2 требует роль finance_invite_admin из infra/postgres/002-invite-role.sql.
Runtime читает и погашает приглашение (UPDATE только used_at/used_by), но не создаёт.
Отдельный invite admin только SELECT/INSERT приглашений, без чтения users/финансов.
У runtime есть DELETE users для password-confirmed удаления аккаунта; каскад не
меняет обычные INSERT/SELECT-only права sync-журналов. Used invite сохраняет used_at,
used_by при удалении пользователя становится NULL.

Имена Flyway приведены к V001/V002/V003/V004 без изменения SQL/description;
совместимость со старой history проверена без repair. См. [структуру](project-structure.md).
