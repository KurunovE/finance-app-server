# Подтверждение email и восстановление пароля

Регистрация по приглашению теперь отвечает **201 Created без тела и токенов**. Аккаунт уже создан к моменту ответа;
отложена только отправка письма, поэтому 202 для регистрации не используется. В одной
транзакции создаются пользователь без email_verified_at, устройство, категории,
журнал и verify token. Login неподтверждённого пользователя возвращает обычный 401.
POST /api/v1/auth/email/verify с `{ "token": "..." }` подтверждает email и отвечает
204; затем клиент выполняет login. Старые аккаунты V2 также должны подтвердить email:
V3 не считает их проверенными и отзывает прежние семьи.

POST /api/v1/auth/email/request и POST /api/v1/auth/password/forgot принимают email
и отвечают одинаковым 202 `{ "status": "ACCEPTED" }` для неизвестного, disabled,
неподходящего и подходящего аккаунта. Это одинаковый HTTP-ответ, не гарантия постоянного
времени ответа. SMTP выполняется асинхронно. Cooldown — 60 секунд на пользователя и
назначение в БД, общий IP limiter сохранён. Forgot выдаёт reset только verified/ACTIVE.

Токены — 32 случайных байта, base64url без padding; в БД только SHA-256. Verify TTL
по умолчанию 24 часа (максимум 7 дней), reset 15 минут (максимум 1 час). Повторная
выдача аннулирует предыдущую ссылку того же назначения. Использованный, просроченный,
неизвестный или неверного назначения токен даёт 400 INVALID_OR_EXPIRED_TOKEN.

POST /api/v1/auth/password/reset принимает `{ "token": "...", "password": "..." }`.
Пароль проходит прежнюю политику 12–128/частые пароли/Argon2id. Успех — 204: пароль,
погашение action tokens и отзыв **всех** семей пользователя коммитятся атомарно.
Слабый пароль — 422, токен остаётся действующим. Два одновременных reset одной ссылкой
дают один успех. Старые JWT/refresh больше не действуют; автоматического входа нет.

Ссылки содержат токен во fragment `#token=...`, не в query/path. GET не меняет данные;
клиент извлекает fragment и явно отправляет POST, не записывает ссылку в аналитику/логи,
показывает понятное подтверждение перед сменой пароля. MAIL_PUBLIC_URL — фиксированный
адрес клиента, не Host запроса; HTTPS обязателен кроме localhost/loopback. UI страниц
/verify-email и /reset-password здесь не реализован: backend API и SMTP готовы для клиента.

Письма отправляет JavaMail после commit через ограниченную RAM-очередь (100 задач,
1–2 worker). Нет гарантии доставки при падении процесса/ошибке SMTP/переполнении;
пользователь повторно запрашивает письмо после cooldown. В логах только безопасный
тип ошибки, без recipient/токена/SMTP response. Включать SMTP protocol debug нельзя.

Для local запустить Mailpit (перехватывает письма без внешнего relay):

```sh
docker compose --env-file infra/.env -f infra/compose.yaml --profile mail up -d
```

SMTP 127.0.0.1:1025, inbox http://127.0.0.1:8025. SMTP_HOST/SMTP_PORT по умолчанию
настроены на него; MAIL_FROM=no-reply@finance.local, MAIL_PUBLIC_URL=http://127.0.0.1:8080.
При отсутствии клиента можно взять токен в локальном inbox и отправить POST вручную.
Mailpit содержит секретные ссылки — не публиковать его UI/SMTP в сеть.

Prod требует SMTP_HOST/SMTP_PORT (587), SMTP_USERNAME/SMTP_PASSWORD, MAIL_FROM и
MAIL_PUBLIC_URL. Включены SMTP AUTH, обязательный STARTTLS, проверка имени сертификата,
connect/read/write timeout 3 секунды. Реальный SMTP provider/домен, доставляемость,
SPF/DKIM/DMARC и клиентские ссылки проверяются отдельно перед публичным запуском.
Локальный JAR smoke отключает AUTH/STARTTLS **только** для своего Mailpit на loopback;
HTTPS API при этом проверяется с CA/hostname. Внешние письма в проверках не отправляются.
