# Восстановление БД и протокол эпох

UUID `epoch` обозначает историю сервера. Счётчик seq сам по себе не определяет историю:
после старого snapshot тот же номер может соответствовать другому событию. Все sync
запросы передают `X-Recovery-Epoch`; каждая операция outbox содержит собственный
неизменяемый `epoch`, зафиксированный при создании. Access JWT дополнительно содержит
`ep`. Отсутствующий header — 428, некорректный UUID — 400, другая эпоха — 409
RECOVERY_EPOCH_MISMATCH, старая операция — 409 OPERATION_EPOCH_MISMATCH.

## Действия оператора

Остановить writers и закрыть сетевой доступ; восстановить копию в изолированную БД.
Обновить схему до V4, сохранив Flyway history, роли и весь journal/idempotency state.
Нельзя открывать API непосредственно после pg_restore с чужой recovery_state.
Резервные копии создаёт владелец своими средствами. Независимо от наличия recovery
metadata в копии выполнить `recovery-prepare` до открытия API. При старте приложения
отсутствие строки состояния автоматически создаёт новую эпоху RECOVERY,
отзывает все семьи и action tokens и сбрасывает отметки устройств. Health при исправных
БД/SMTP остаётся UP, а API отвечает 503 RECOVERY_MAINTENANCE. Health не означает READY.
Для любой чужой/старой копии с включённой metadata всё равно обязателен prepare до открытия сети.

CLI запускается отдельным процессом, не поднимает HTTP/Flyway. Передать только ему
RECOVERY_DB_URL, RECOVERY_DB_USER=finance_migrator и RECOVERY_DB_PASSWORD из приватного
окружения; не добавлять admin credentials в web runtime. Схема должна быть уже обновлена.

```sh
java -jar backend/build/libs/finance-tracker-backend-0.1.0-SNAPSHOT.jar recovery-prepare
java -jar backend/build/libs/finance-tracker-backend-0.1.0-SNAPSHOT.jar recovery-status
java -jar backend/build/libs/finance-tracker-backend-0.1.0-SNAPSHOT.jar recovery-activate --epoch <UUID-из-status> --reconciled
```

Prepare всегда создаёт новую эпоху, отзывает семьи/action tokens, удаляет только
временный прогресс replay. Финансовые записи, sync_changes и sync_operations сохраняются.
Эксклюзивная advisory transaction lock ждёт завершения начатых writers; runtime берёт
shared lock до user/state locks. Runtime не может менять metadata или вызывать admin-функции.

Перед activate оператор сверяет точку восстановления, целостность журнала, список
удалённых/отключённых пользователей из независимого источника и план возврата потерянных
операций. `--reconciled` — явное подтверждение оператора, не автоматическая сверка.
Неверная epoch/phase не активируется. До завершения сверки оставлять RECOVERY.
После activate заново войти; прежние JWT/refresh и ссылки email/reset не действуют.

## Обязательная последовательность клиента

1. На смене epoch, 409 FULL_RESYNC_REQUIRED или восстановлении после 401 остановить
   обычный sync. Не менять epoch у существующих outbox-операций и не очищать локальную БД.
2. Сохранить независимую локальную recovery-копию **всех** записей, cursor, outbox,
   operationId и результатов, включая ранее подтверждённые сервером операции. Иначе
   подтверждённые после snapshot изменения могут пропасть при замене локального состояния.
3. После login вызвать GET /api/v1/sync/status. Новые устройства и все устройства после
   V4/recovery требуют full resync. POST /api/v1/sync/recovery/start с текущим header
   возвращает recoveryId, epoch, cutoffSeq, deliveredSeq. Повтор start возвращает
   существующий незавершённый сеанс этого устройства.
4. GET /api/v1/sync/recovery/{id}/pull?cursor=0&limit=100, затем страницы до cutoff.
   Cursor и применённую страницу сохранять атомарно в **отдельной** восстанавливаемой
   локальной БД. Применять UPSERT и DELETE tombstones последовательно; старую копию
   не перезаписывать. Limit 1–200; пропуск за deliveredSeq запрещён; повтор страницы разрешён.
   Cutoff фиксирован: новые параллельные изменения придут обычным pull после ack.
5. Изолировать весь старый outbox для сверки. POST /api/v1/sync/recovery/{id}/ack с
   `{ "lastCursor": <cutoff>, "localCopyPreserved": true, "pendingOperationsQuarantined": true }`.
   Сервер проверяет, что все страницы выданы до cutoff, обе декларации обязательны.
   Пока ack не выполнен, обычные push/pull возвращают FULL_RESYNC_REQUIRED.
6. Продолжить pull с cutoff и создавать только новые операции текущей epoch. Старые
   подтверждённые/pending действия сверять отдельно с новой серверной историей. Для
   одобренного повторного действия создать **новый** operationId после проверки сущности,
   логических ключей и версий. Не переотправлять автоматически неизвестный старый CREATE.

Сеанс привязан к user/device/epoch, доступ другого устройства или аккаунта — 404.
Повтор ack безопасен. Сервер проверяет доставку страниц и декларации клиента, но не
может проверить физическую сохранность локального файла. Android-клиента здесь нет;
его реализация и UX сверки нужны перед использованием этого протокола пользователями.

Реальный локальный тест сохраняет дамп, подтверждает новую операцию, восстанавливает
старый дамп и перезапускает сервер с тем же JWT-ключом. Проверяются RECOVERY, новая
epoch, отзыв прежнего доступа, полный replay и отказ повторить старую операцию.
Recovery не восстанавливает данные, отсутствующие во всех доступных копиях, и не
обещает RPO=0. WAL/PITR и независимый реестр удалений остаются отдельными задачами.
