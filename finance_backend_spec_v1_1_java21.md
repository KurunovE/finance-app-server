**Версия:** 1.5  
**Дата:** 31.10.2026  
**Статус:** спецификация реализации; условия эксплуатации — в `backend/docs/operations.md`. По новому решению пользователя Spring Boot 3.5.16 / Spring 6.2.19 с JUnit 5.13.4.
**Область работ:** только сервер приложения личного учёта расходов, его база данных, REST API, безопасность, автоматизированные тесты и серверная инфраструктура.

## 1. Роль, задача и ограничения AI-агента

Ты — senior Java/Kotlin backend engineer, системный архитектор, инженер по безопасности и автоматизированному тестированию. **Реализуй и проверь работоспособный backend**, а не пустой каркас, набор заглушек или произвольную архитектуру.

Приоритеты решений в таком порядке:

1. Невозможность доступа одного аккаунта к данным другого.
2. Сохранность и корректность финансовых данных при обрывах сети, повторах и конкуренции.
3. Простая, понятная архитектура и малая стоимость сопровождения.
4. Тестируемость, наблюдаемость и безопасная эксплуатация.
5. Производительность при обычной пользовательской нагрузке.

Соблюдай **ООП, SOLID, DRY, KISS, принцип минимальных привилегий**. Пиши **чистый, компактный, читаемый код**. Паттерны и абстракции вводи, только если они реально решают задачу. Не используй микросервисы, Kafka, Redis, Kubernetes, GraphQL, event sourcing или собственную реализацию шифрования только ради «масштабируемости». Для доступа используй JWT HS256, для обновления — одноразовые opaque refresh-токены с серверными семьями сессий согласно разделу 7.

**Правила работы:**

- Не меняй JDK: сервер собирается и запускается на **JDK/JRE 21**. Запрещены возможности Java 22+ и требование Java 25.
- Используй Java и Kotlin в **одном JVM-процессе**. Оба языка должны реализовывать осмысленную, тестируемую часть приложения.
- Прежде чем подключить новую библиотеку, проверь официальную документацию и совместимость; фиксируй версии, не используй динамические версии.
- Каждая реализованная пользовательская функция должна иметь тесты нормального пути, негативного пути и важных граничных условий.
- Не симулируй результаты тестов; в отчёте приводи **реально выполненные команды и результаты**. При невозможности запустить Docker, Testcontainers или Gradle явно фиксируй блокирующую причину.
- Для каждого этапа: реализуй → протестируй → обнови документацию → зафиксируй сделанное → переходи дальше.
- Никаких настоящих паролей, токенов, пользовательских данных или ключей в Git, выводе сборки, логах и примерах. Исключение — однократный вывод нового приглашения администратору командой create-invite; это результат команды, а не обычный лог (раздел 10.4).

**Ожидаемый результат** — запускаемый `backend/`, папка `infra/`, SQL-миграции, тесты (unit + integration + API/security + concurrency), автоматическая проверка покрытия ≥ 80%, GitHub Actions, OpenAPI-контракт и эксплуатационная документация.

## 2. Функциональные границы MVP

### Должно быть реализовано

1. Регистрация пользователя с email, паролем, одной базовой валютой и валидным одноразовым кодом-приглашением от администратора.
2. Вход с привязкой к устройству, JWT access, ротация refresh, отзыв семьи при replay/logout, отключение и удаление аккаунта.
3. Категории расходов: системные стартовые категории персонально для нового пользователя, создание, переименование, архивирование.
4. Расходы: создание, изменение, удаление, проверка принадлежности категории.
5. Общий месячный бюджет и месячные лимиты по категориям: установить, изменить, убрать.
6. Обмен изменениями с Android-клиентом: `push` и `pull`, версии объектов, курсор и журнал изменений.
7. Идемпотентность операций при повторной отправке и при конкурентных запросах.
8. Изоляция данных по аккаунтам в Spring-сервисах, SQL и PostgreSQL RLS.
9. Безопасное хранение, TLS, резервные копии и минимальная диагностика ошибок.
10. Гарантированный тестовый quality gate не ниже 80% line coverage.

**Не делать в MVP:** банковские интеграции, доходы, семейные счета, инвестиции, платёжные операции, автоматическую категоризацию, AI/LLM, отдельный сервер голосового помощника, прогнозы, сложную систему ролей и администрирования. Администратор создаёт приглашения локальной командой `create-invite` (раздел 10.4), без отдельного admin HTTP API. Для будущего голосового ввода достаточно существующего контракта создания расхода.

**Граница ответственности:** Android автономно записывает изменения в свою локальную очередь; сервер **не** управляет локальным WorkManager/Room. Сервер обязан предоставить надёжные `push/pull`-семантики, которые позволяют клиенту восстановиться после любой потери HTTP-ответа. Создание аккаунта впервые без интернета невозможно.

| База | **PostgreSQL 18.x** | Транзакции, ограничения, RLS, блокировки, индексы |

| Unit-тесты | JUnit Jupiter 5.13.4 (отдельно закреплённый BOM по решению пользователя) + Assertions | Бизнес-правила без инфраструктуры |
| Integration/API | Spring Boot Test, MockMvc / реальный HTTP, **Testcontainers PostgreSQL**, JUnit Jupiter | Проверка настоящего SQL, RLS, транзакций и API |

| CI | GitHub Actions (Java 21) | Автоматическая сборка, тесты, покрытие |

**Не вводить JPA/Hibernate** без обоснования: явные SQL-запросы важны для изоляции данных и `UPDATE ... WHERE user_id = ... AND version = ...`. Использовать **Spring MVC**, не подключать WebFlux. Использовать `spring-boot-starter-web` и `spring-boot-starter-test` Boot 3.5.

**Проверка зависимостей перед созданием build:** Spring Boot 3.5.16, Kotlin 2.4.21 и доступность конкретных артефактов сверять с официальной документацией. Не копировать случайный `build.gradle.kts` из версии Boot 3: там могут отличаться названия starter'ов и тестовых модулей. Установить Java/Kotlin toolchain на 21, CI тоже 21. `org.gradle.java.home` со специфическим локальным путём не коммитить.

## 4. Архитектура backend и правила кода

**Решение: модульный монолит, один Gradle backend-модуль.** Разделение — по бизнес-областям, без циклических зависимостей и десятков интерфейсов «на всякий случай».

```text
Android / защищённая локальная БД / outbox
                   │
             HTTPS (TLS)
                   │
      TLS reverse proxy (production)
                   │
         Spring Boot / Java 21
          ├─ security (Java)
          ├─ auth     (Java)
          ├─ api      (Java)
          ├─ finance  (Kotlin)
          ├─ sync     (Java)
          └─ persistence (Java, Spring JDBC)
                   │
          PostgreSQL 18 + RLS
         encrypted disk + backups
```

**Распределение языков:** Java: REST-контроллеры, SecurityFilterChain, auth/session, JDBC-репозитории, синхронизационный протокол и транзакционные границы. Kotlin: финансовая доменная модель и операции над расходами, категориями, лимитами и бизнес-валидация. Kotlin вызывается из Java непосредственно, репозитории предоставляются как Java-интерфейсы. Не размещай одну и ту же бизнес-логику параллельно на обоих языках.

### Структура по слоям

Размещение тестов `java`/`kotlin` может быть сгруппировано по домену вместо папок `unit/integration`, если имена и правила запуска остаются понятными. В Java/Kotlin не дублировать DTO и основные типы с разной семантикой. Для Kotlin использовать `data class`, `val`, проверяемые nullability, без ненужных фабрик/обобщённых базовых классов.

### Обязательные инженерные стандарты: чистый и компактный код

**Эти требования обязательны для всех этапов и всех pull request.** Цель — не максимальное количество слоёв, интерфейсов или паттернов, а минимальная сложность при сохранении корректности, безопасности, возможности тестировать и расширять backend.

1. **Чистота и читаемость.** Используй содержательные названия классов, методов, полей и переменных. Метод должен решать одну понятную задачу; класс — отвечать за одну связную область ответственности. Не допускай «божественных объектов», скрытых побочных эффектов, дублирования правил и неиспользуемого кода. Нетривиальные бизнес-правила должны быть явно видны и документированы тестами.
2. **Компактность без ухудшения ясности.** Выбирай самое короткое **понятное** решение, а не искусственно минимальное число строк. Не дроби простую операцию на цепочку одношаговых методов и не создавай лишние DTO, мапперы, обёртки или уровни вызова. Избегай чрезмерной вложенности; используй раннюю проверку и возврат, когда это улучшает чтение.
3. **ООП и SOLID по назначению.** Поддерживай инкапсуляцию и явно выраженные инварианты. Применяй SRP и DIP в реальных границах ответственности; расширяемость обеспечивай через композицию и разумные контракты. Соблюдай OCP, LSP и ISP там, где есть реальные точки вариативности, а не путём создания абстрактных классов и интерфейсов для каждого сервиса. Никаких сеттеров, открывающих неконтролируемое изменение финансового состояния.
4. **DRY и KISS.** Общую бизнес-логику реализуй в одном месте. Не объединяй непохожие операции только потому, что сейчас у них одинаковые несколько строк; небольшое осмысленное повторение лучше ложной универсальности. Предпочитай стандартные возможности Java 21, Kotlin, Spring и PostgreSQL самописной инфраструктуре.
5. **Паттерны — только с доказуемой пользой.** Используй Repository для изоляции SQL, Dependency Injection для зависимостей и явные application services для транзакционных сценариев. Применяй Strategy только при наличии разных взаимозаменяемых алгоритмов, Adapter — при подключении реального внешнего провайдера, Factory — при действительно сложном создании объектов. Не вводи паттерны «на будущее», фабрики для простых конструкторов, generic CRUD framework, CQRS/event sourcing, посредников и обработчиков ради формального соответствия учебнику. **Для каждого нового паттерна агент должен объяснить конкретную проблему, которую он решает, и почему прямое решение хуже.**
6. **Контролируй зависимости.** Используй constructor injection. Не добавляй интерфейс для реализации, если нет полезной границы/возможности подмены, а простого класса достаточно. Избегай циклических зависимостей и протаскивания Spring/HTTP/JDBC типов в финансовую доменную логику. Java 21 `record` и Kotlin `data class` используй для простых неизменяемых значений; исключения и наследование — только с понятной семантикой.
7. **Простота не отменяет безопасность.** Не сокращай проверки доступа, валидацию, транзакционность, RLS, аудит чувствительных изменений и обработку конфликтов ради меньшего количества строк. Дублирование защиты на разных уровнях (API + SQL/RLS) здесь намеренно и необходимо. Явно обрабатывай ошибки без общих `catch (Exception)` с сокрытием причины, не логируй секреты и персональные финансовые записи.
8. **Тестируемость без переусложнения.** Тестируй наблюдаемое поведение и бизнес-инварианты, не внутренние вызовы ради моков. Не создавай абстракции исключительно ради искусственного упрощения теста, если сценарий можно проверить через обычный unit- или PostgreSQL integration-тест. Минимум **80% line coverage** (общий и по критическим областям) обязателен, но не оправдывает бессмысленные тесты и ухудшение дизайна.
9. **Обоснованность библиотек.** Перед добавлением зависимости сначала проверь, закрывают ли задачу уже подключённые Spring/Kotlin/Java/PostgreSQL механизмы. Если нет, изучи официальную документацию и совместимость с JDK 21, опиши, зачем библиотека нужна. Не подключай библиотеку ради одного простого метода, который прозрачнее написать стандартными средствами.

**Проверка при код-ревью:** агент обязан перед завершением каждого этапа пройтись по изменённым классам и убрать избыточные слои, неиспользуемые типы, копипасту, необоснованные паттерны и зависимости. При этом все тесты, защита данных и инварианты должны продолжать работать. При выборе двух равно корректных вариантов предпочитай вариант с меньшим количеством сущностей, зависимостей и скрытых правил. **Не вводи искусственные лимиты строк на класс или метод:** важнее читаемость и ответственность.

### Непереговорные инварианты

- **Ни один пользовательский `user_id` не берётся из HTTP-запроса**. Он извлекается исключительно из сервером подтверждённого `AuthenticatedPrincipal`.
- Чужой UUID никогда не даёт права на чтение, правку, удаление, создание связанной записи или получение чужого snapshot/события.
- Любая финансовая запись принадлежит одному пользователю; FK между пользовательскими таблицами **составные** по `(user_id, id)`.
- Денежные значения — `Long` / `BIGINT` **в минимальных единицах** (копейках/центах), только целые; не `double`, не `float`.
- Редактирование с устаревшей версией не перезаписывает актуальную запись.
- Бизнес-изменение, `sync_operations`, продвижение sequence и `sync_changes` фиксируются одной транзакцией.
- `GET pull` не меняет данные. Идемпотентный повтор `push` с тем же `operationId` не создаёт повторного расхода.
- При сбое сервера уже подтверждённая операция не исчезает; неподтверждённая безопасно повторяется клиентом.

## 5. Предметная модель и бизнес-правила

**Пользователь:** `id` (серверный UUID), `email`, `email_norm`, `password_hash`, `base_currency_code`, `status` (`ACTIVE` / `DISABLED`), `created_at`, `updated_at`. Адрес регистрационной почты и нормализованный адрес различать; явно задокументировать регистронезависимый поиск по email и политику нормализации. Валюту выбрать из фиксированного списка для MVP (например, RUB/EUR/USD), после появления первой финансовой записи менять не разрешать.

**Категория:** `user_id`, `id`, `name`, `normalized_name`, `archived`, `sort_order`, `version`, audit timestamps. Название в пределах установленной длины (например, 1–80 символов). Уникальность нормализованных названий на одного пользователя. Архивировать, а не удалять категорию с историей расходов. Новые расходы к архивной категории запрещены; история остаётся доступной.

**Расход:** `user_id`, `id`, `category_id`, `amount_minor`, `occurred_on`, `note?`, `version`, audit timestamps. `amount_minor > 0`; сумма не должна переполнять `long`. Дата — `DATE`, не UTC timestamp (пример: `2026-10-31`). Заметка опциональна, максимум 500 символов; входные данные нормализовать и валидировать. `category_id` должен принадлежать этому пользователю и быть активен для создания или изменения категории расхода.

**Общий бюджет:** `user_id`, `id`, `month_start`, `limit_minor`, `version`; ровно один на `(user_id, month_start)`. **Бюджет категории:** такой же, плюс `category_id`, уникален по `(user_id, month_start, category_id)`. `month_start` — первое число месяца. `limit_minor > 0`. Удаление бюджета означает «лимит не задан», а не «ноль».

**Расчёты и даты:**

- Суммы и лимиты всегда в минимальных единицах валюты. Клиент и сервер согласуют валюту и её масштаб; в MVP только одна базовая валюта на пользователя.
- Дневная и месячная группировка по `occurred_on`, выбранный месяц — полуинтервал `[firstDay, nextMonthFirstDay)`.
- `spent = SUM(amount_minor)`, `remaining = budget - spent`, `overrun = max(0, spent - budget)`; без бюджета `remaining/overrun` не вычислять как фиктивный ноль.
- Проверять переполнение: в Java/Kotlin — `Math.addExact`/проверенное длинное целое, в PostgreSQL — корректное преобразование агрегатов (например, SQL `SUM(bigint)` возвращает `numeric`).
- **Источник истины финансовых записей — сервер**, а агрегаты пользовательского интерфейса вычисляются из локальной копии Android, включая pending изменения. Не добавляй отдельную аналитическую БД или тяжёлый `/reports` API для MVP.
- Удаление расхода фиксируется в sync-журнале как tombstone; иначе другой телефон не узнает об удалении.

## 6. PostgreSQL: таблицы, миграции и безопасность

### Таблицы (обязательный минимум)

| Таблица | Назначение | Ключевые ограничения |
|---|---|---|
| `users` | Профиль, статус и парольный хеш | `id PK`, уникальный `email_norm`, `status IN (ACTIVE, DISABLED)` |
| `registration_invites` | Одноразовые приглашения администратора | `code_hash UNIQUE`, `expires_at`, `used_at`; исходный код не хранить |
| `devices` | Устройства аккаунта | `PK(user_id,id)`, `user_id FK ON DELETE CASCADE` |
| `auth_sessions` | Семьи сессий устройств и текущий refresh | `family_id PK`, `user_id FK ON DELETE CASCADE`, составной FK `(user_id,device_id)` к devices, `access_jti UNIQUE`, `refresh_token_hash UNIQUE`, сроки/отзыв |
| `used_refresh_tokens` | Использованные refresh-токены для replay detection | `token_hash PK`, `family_id FK ON DELETE CASCADE`, `used_at`, срок хранения |
| `categories` | Персональные категории | `PK(user_id,id)`, `UNIQUE(user_id,normalized_name)` |
| `expenses` | Расходы | `PK(user_id,id)`, `FK(user_id,category_id)` к `categories`, `amount_minor > 0` |
| `monthly_budgets` | Общий месячный лимит | `PK(user_id,id)`, `UNIQUE(user_id,month_start)` |
| `category_budgets` | Месячный лимит категории | `PK(user_id,id)`, `UNIQUE(user_id,month_start,category_id)`, составной FK категории |
| `user_sync_state` | Счётчик событий одного аккаунта | `user_id PK`, `last_seq >= 0` |
| `sync_operations` | Запоминание результата обработанной операции | `PK(user_id,operation_id)`, `request_hash`, `result_status`, `result_payload` |
| `sync_changes` | Журнал UPSERT/DELETE, включая tombstones | `PK(user_id,seq)`, payload, version, timestamp |

**Изменение существующей схемы:** этап 1 уже реализован с прежними opaque access-токенами. Новые auth-требования внести следующими Flyway-миграциями (V2 и далее); применённую V1 не переписывать. Удалить необходимость `access_token_hash`, добавить приглашения, устройства, семьи, `access_jti`, статус пользователя и каскадные FK. Это требования к дальнейшей реализации, а не описание уже выполненного кода.

**Миграции:** SQL Flyway с `CREATE TABLE`, `CHECK`, `FK`, индексами, `ENABLE/FORCE ROW LEVEL SECURITY`, RLS policy и разрешениями ролей. Стартовые категории создаются в транзакции регистрации для конкретного пользователя — **не** как глобальный справочник с общим ID и не через повторяющуюся миграцию. Требовать чистый старт миграций на пустой PostgreSQL 18 и повторный запуск без изменений схемы. Не использовать `ddl-auto=create/update`.

**Индексы:** `expenses(user_id,occurred_on,category_id)`, `expenses(user_id,category_id,occurred_on)`, `sync_changes(user_id,seq)` (покрывается PK при указанном порядке), индексы `auth_sessions(access_jti)`, `auth_sessions(refresh_token_hash)`, `used_refresh_tokens(token_hash)`, приглашений по `code_hash`, семей по пользователю/устройству и отзыву (UNIQUE/PK уже создают соответствующий индекс). Не плодить индексы без запросов/плана выполнения. Для бюджетов — `CHECK (month_start = date_trunc('month', month_start)::date)` либо эквивалентная валидная для PostgreSQL форма (в миграции проверить), `CHECK (limit_minor > 0)`.

### Двойная изоляция пользователей

**Уровень 1 — application:**

```sql
SELECT * FROM expenses
 WHERE user_id = :authenticated_user_id AND id = :expense_id;

UPDATE expenses
   SET amount_minor = :new_amount, version = version + 1
 WHERE user_id = :authenticated_user_id
   AND id = :expense_id AND version = :expected_version;
```

Аналогичный фильтр необходим во всех запросах списка, обновления, удаления, проверки FK, журнале изменений и idempotency. Запись `user_id` при INSERT устанавливает сервер. Чужой/отсутствующий ID для пользователя обрабатывается одинаково (`NOT_FOUND`, без раскрытия чужой записи).

**Уровень 2 — PostgreSQL RLS (defense in depth):**

```sql
ALTER TABLE expenses ENABLE ROW LEVEL SECURITY;
ALTER TABLE expenses FORCE ROW LEVEL SECURITY;

CREATE POLICY expenses_isolation ON expenses
  USING (user_id = NULLIF(current_setting('app.current_user_id', true), '')::uuid)
  WITH CHECK (user_id = NULLIF(current_setting('app.current_user_id', true), '')::uuid);
```

Применить аналогичную политику на **все пользовательские финансовые и sync таблицы**. Таблицы аутентификации обслуживаются только строго ограниченными auth-репозиториями; их внешние API не отдают чужую информацию. Runtime-роль БД не superuser, без `BYPASSRLS`, не владеет пользовательскими таблицами, права `CREATE/ALTER` у неё отсутствуют; отдельная миграционная роль применяет Flyway.

**Критически важно при пуле соединений:** перед работой с пользовательскими данными установить доверенный `userId` внутри **той же PostgreSQL-транзакции/соединения** через `SELECT set_config('app.current_user_id', :verifiedUserId, true)` (`true` = transaction-local). Все бизнес-запросы идут на том же соединении под `@Transactional`; после commit/rollback контекст исчезает. Без установленного контекста доступ **запрещён по умолчанию**. Не использовать `SET` на всю сессию и не полагаться на ThreadLocal без связи с JDBC-транзакцией. Не доверять HTTP-заголовку `X-User-Id` и не считать RLS заменой безопасного SQL (в том числе защиты от SQL injection).

При регистрации сервер генерирует новый `userId`, в контролируемой транзакции создаёт пользователя, устанавливает его transaction-local context и создаёт персональные категории. Проверить этот сценарий с реальной RLS. Каждая бизнес-транзакция устанавливает контекст **один раз до первого пользовательского SQL-запроса**. Явно документировать порядок вызовов сервисов и propagation транзакций.

**Тесты RLS обязательны:** runtime-пользователь БД не читает, не создаёт и не изменяет чужие строки даже при ошибочно отсутствующем application-фильтре; после возвращения соединения в пул контекст прошлого пользователя не сохраняется. Проверить ограничения составного FK на попытке создать расход с категорией другого пользователя.

### Транзакции и удаление

Любой `push` выполняется атомарно для **одной операции**. При создании/изменении/удалении расхода или бюджета в той же транзакции записываются `(user_id,operation_id,request_hash,result)` и новое событие `(user_id,seq,...)`. Удаление — удаление актуальной записи плюс tombstone в `sync_changes` с `entity_version = предыдущая версия + 1`. Для категории — архивирование через UPSERT. В MVP журнал изменений и результаты idempotency **не удалять** без отдельного протокола safe-retention и ресинхронизации: старый телефон должен иметь возможность догнать сервер. Исключение — явное необратимое удаление всего аккаунта по разделу 7: все его финансовые и sync-данные удаляются каскадно; это не обычная retention/очистка журнала.

## 7. Авторизация и управление сессиями

### Регистрация и вход

Регистрация только с валидным кодом-приглашения: одноразовый, **128 бит** криптографической случайности, TTL по умолчанию **7 дней**. Создаёт администратор командой `create-invite` (см. 10.4); в БД хранится только SHA-256-хеш кода. Проверка срока и атомарное погашение приглашения входят в транзакцию регистрации. Отсутствующий, неверный, истёкший или использованный код не позволяет создать аккаунт.

Публичные конечные точки: `POST /api/v1/auth/register`, `/api/v1/auth/login`, `/api/v1/auth/refresh`. Регистрация публична на уровне HTTP, но требует приглашение. Остальные `/api/v1/**` и `DELETE /v1/me` требуют действующей аутентификации, кроме явно разрешённых технических health endpoints. Политика Spring Security — `denyAll` для неизвестных маршрутов. Самописную криптографию не писать.

**Пароль:** длина **12–128 символов**, проверка по встроенному списку частых паролей, без правил «обязательно цифра/символ». Не обрезать, не менять регистр и не нормализовать пароль молча. Хеш — **Argon2id**: `Argon2PasswordEncoder`, salt **16 Б**, hash **32 Б**, parallelism **1**, memory **≥ 19 456 КиБ**, iterations **≥ 2**, не ниже минимума OWASP. Формат хранения — `DelegatingPasswordEncoder` с идентификатором алгоритма для будущего апгрейда. Поддержать проверку необходимости обновления хеша при успешном входе. Пароль, включая подтверждение удаления аккаунта, не логируется, не передаётся в URL и не возвращается в ответах.

**Email / username:** логин остаётся по email, отдельное поле имени пользователя не вводится. `username` в ключе brute-force limiter означает `email_norm`. Проверить формат/длину email и задокументировать нормализацию для регистронезависимого поиска; уникальность гарантирует БД. Неизвестный email, неверный пароль и отключённый аккаунт имеют унифицированный внешний ответ без выдачи токенов.

### JWT access и семьи refresh-токенов

- **Access-токен:** JWT **HS256**, TTL **15 минут**, claims `sub` (`userId`), `did` (`deviceId`), `jti`, `ep` (recovery epoch); также обязательны `iat` и `exp` для проверки срока. Передача — `Authorization: Bearer`. Разрешён только HS256: отклонять `alg=none`, другой алгоритм, неверную подпись, истёкший токен, неизвестный `kid`, некорректные или отсутствующие обязательные claims.
- Ключ подписи — случайный секрет **≥ 256 бит из файла-секрета**, с минимальными правами чтения; не пароль и не строка по умолчанию в конфигурации. Поддержать `kid` в JWT header и набор ключей для ротации: новые JWT подписываются текущим ключом, старый доступен только для проверки до истечения выданных им токенов. `kid` выбирает ключ из настроенного набора и не используется как произвольный путь/URL.
- **Refresh-токен:** непрозрачный, **256 бит** криптографической случайности, кодирование **base64url**; в БД только **SHA-256-хеш**, TTL **60 дней** от выдачи каждого токена. Используется только для `/api/v1/auth/refresh`.
- При login создаётся или подтверждается принадлежащее аккаунту устройство и создаётся семья `family_id`. Для одного устройства одновременно действует одна неотозванная семья; новый login этого устройства отзывает предыдущую. `did` не служит самостоятельным доказательством личности: его принадлежность устанавливает сервер.
- Refresh одноразовый: транзакция блокирует семью, проверяет статус пользователя, срок и отзыв, помечает старый refresh использованным и выдаёт новый **в той же `family_id`**, вместе с новым JWT и `jti`. Конкурентные refresh не создают две действительные ветви. Использованные хеши сохраняются всё время активности семьи, чтобы обнаруживать replay.
- Повторное предъявление уже использованного настоящего refresh — признак кражи: **отзыв всей семьи (сессии устройства)**. Случайный неверный токен не отзывает чужую семью. Отзыв должен закоммититься, даже если HTTP-ответ на replay — `401`.
- **Logout отзывает семью** текущего устройства; повтор не меняет итог. Сохраняется требование немедленного отзыва access после logout/replay: после проверки JWT сервер сверяет `sub`, `did`, `jti` с текущей неотозванной семьёй в БД. JWT не считается полностью stateless; положительный кэш не должен оставлять окно после отзыва. При refresh текущий `access_jti` меняется, предыдущий JWT этой семьи больше не принимается.
- Проверять срок, отзыв и принадлежность устройства/семьи; для неавторизованного запроса — `401`. В БД не хранить JWT целиком или его подпись; сохранять только нужные идентификаторы и сроки. Токены, `Authorization`, приглашения и секреты скрыть в логах, tracing, метриках и исключениях.

### Brute-force и доверенный IP

Не более **5 неудачных логинов на пару `(username + IP)` за 15 минут**. После пятой ошибки последующие попытки до освобождения окна получают **429 с `Retry-After`**; счётчик и проверка лимита атомарны при конкурентных запросах. Общий лимит на IP — **60 запросов/мин по умолчанию** для публичного API, включая регистрацию и refresh. Значение и область действия явно настраиваются; ошибки не раскрывают существование аккаунта.

В production IP берётся только из заголовков **доверенного прокси Caddy**. Caddy очищает/перезаписывает клиентские forwarded headers, прямой внешний доступ к backend закрыт, доверенные адреса прокси заданы явно. Явно настроить `server.forward-headers-strategy` вместе с механизмом ограничения доверенных прокси; одна настройка обработки заголовков не делает их доверенными. Заголовки от недоверенного отправителя не влияют на IP limiter. Для local/test без прокси используется адрес непосредственного соединения. Для одного инстанса допустим потокобезопасный локальный limiter; для нескольких нужна общая согласованная реализация.

### Отключение и удаление аккаунта

**Блокировка/отключение:** `status = DISABLED` отзывает все семьи/сессии пользователя. Статус обязательно проверяется при refresh; новый login отключённого аккаунта запрещён. Отозванные семьи также исключают использование уже выданных JWT по правилу проверки сессии выше.

**Удаление аккаунта:** `DELETE /v1/me` с текущим паролем в JSON body и действующим access-токеном. Проверить пароль, затем в одной транзакции каскадно удалить пользователя, устройства, семьи, текущие и использованные refresh-токены, категории, расходы, бюджеты и все sync-данные. Термин `sync_record` здесь означает набор `user_sync_state`, `sync_operations`, `sync_changes`; отдельную дублирующую таблицу не создавать. Связанные с пользователем данные удаляются через проверенные `ON DELETE CASCADE`; действие не должно затрагивать чужой аккаунт. В новой миграции выдать runtime необходимые права удаления users; DELETE выполняется только по UUID подтверждённого principal после проверки пароля, а каскад журналов не требует расширять их обычные INSERT/SELECT-права. Для приглашения оставить факт погашения `used_at`, чтобы удаление аккаунта не сделало код повторно действующим; пользовательская ссылка при её наличии очищается.

Успех — **204 No Content**. Неверный пароль — **403** с безопасным кодом отказа без частичного удаления; применить защиту от перебора и к подтверждению пароля для удаления. Операция **необратима**. До подтверждения клиент предупреждает, что **локальные данные на телефоне остаются**; сервер не обещает удаление Room/outbox на устройствах. Удалённый аккаунт не может снова отправить эти данные старой сессией. Серверные backup-копии подчиняются документированной политике хранения; восстановление не должно возвращать доступ удалённому аккаунту.

**Офлайн:** Android продолжает работать в локальном хранилище после предыдущего входа, даже если сервер сейчас недоступен. Истечение/отзыв сессии запрещает *отправку* на сервер до повторного входа, но **не должно удалять локальную очередь**. Сервер не принимает «офлайн-логин по паролю» напрямую.

**До публичного production-релиза:** реализовать и протестировать подтверждение email и безопасное восстановление пароля одноразовыми короткоживущими токенами, анти-enumeration и отзывом сессий после reset. Для внутреннего прототипа допускается заглушка внешнего почтового транспорта за интерфейсом, но **публичный релиз без этих сценариев заблокирован**. Не строить собственную универсальную email-платформу.

## 8. Контракт REST API v1

Базовый префикс существующих endpoints — `/api/v1`; отдельный явно заданный путь удаления аккаунта — **`DELETE /v1/me`**. В таблице ниже пути auth/sync и GET /me относительны к `/api/v1`, пути `/v1/me` и `/actuator/health` — абсолютные. Формат: только JSON/UTF-8, UUID в строковом формате, `LocalDate` в `YYYY-MM-DD`, UTC `Instant` в ISO 8601, суммы — целые `amountMinor`, версии — положительные `long`. Стандартная ошибка без чувствительных данных: `{ "code": "...", "message": "...", "requestId": "..." }`. Никаких Java stacktrace/SQL наружу.

| Метод | Endpoint | Доступ | Поведение |
|---|---|---|---|
| POST | `/auth/register` | публичный + inviteCode | Атомарно погасить приглашение, создать пользователя и стартовые категории, очередь verify email; 201 без токенов |
| POST | `/auth/login` | публичный | Проверить пароль/status/email_verified и устройство, создать семью, выдать JWT и refresh |
| POST | `/auth/refresh` | с refresh token | Проверить status, одноразово ротировать refresh в той же семье; replay отзывает семью |
| POST | `/auth/logout` | с access token | Отозвать собственную семью устройства |
| GET | `/me` | авторизован | `id`, `email`, `baseCurrencyCode` текущего пользователя |
| DELETE | `/v1/me` (абсолютный путь) | access token + пароль в JSON | Необратимо удалить свой аккаунт и связанные данные; 204 |
| POST | `/sync/push` | авторизован | Применить 1–50 операций с отдельными результатами |
| GET | `/sync/pull?cursor=0&limit=200` | авторизован | Выдать изменения текущего аккаунта по порядку |
| GET | `/actuator/health` | технический | Без секретов и лишней диагностики |

Регистрация принимает `inviteCode`, `email`, `password`, `baseCurrencyCode` и `deviceId`; login — `email`, `password`, `deviceId`; refresh — `refreshToken`. Успех выдачи токенов содержит `accessToken`, `refreshToken`, `tokenType: Bearer`, `expiresIn: 900`. `DELETE /v1/me` принимает `{ "password": "..." }` только по HTTPS; body исключается из логов. Реальные пароли/коды/токены в примерах не публиковать.

**Не создавать альтернативные финансовые CRUD endpoints** в MVP: изменение данных клиента проходит через sync, иначе появятся две неэквивалентные схемы версий/идемпотентности. Для первичной загрузки клиент выполняет recovery start/pull/ack по разделу 14, затем обычный pull с cutoff. Состояние категории и бюджета возвращается тем же механизмом.

### `POST /api/v1/sync/push`

```json
{
  "operations": [
    {
      "operationId": "019abc31-1100-7000-8000-000000000001",
      "entityType": "EXPENSE",
      "entityId": "019abc31-2200-7000-8000-000000000002",
      "action": "CREATE",
      "expectedVersion": null,
      "data": {
        "amountMinor": 12550,
        "categoryId": "019abc31-3300-7000-8000-000000000003",
        "occurredOn": "2026-10-31",
        "note": "Продукты"
      }
    }
  ]
}
```

**`entityType`:** `EXPENSE`, `CATEGORY`, `MONTHLY_BUDGET`, `CATEGORY_BUDGET`; **`action`:** `CREATE`, `UPDATE`, `DELETE` (для категории — архивирование/UPDATE). Каждая операция имеет `operationId` (стабильный при повторах) и `entityId` (стабильный UUID, сгенерирован на клиенте). Поля payload строго зависят от типа. Для `CREATE` `expectedVersion=null`; для `UPDATE` и `DELETE` — актуальная положительная `expectedVersion`.

**Ответ на каждую операцию:** `{operationId, status, entityVersion?, serverSnapshot?, code?}`. `status`: `APPLIED`, `ALREADY_APPLIED`, `CONFLICT`, `VALIDATION_ERROR`, `NOT_FOUND`. На уровне запроса корректный пакет возвращает results в порядке поступления; одна конфликтная операция не откатывает другие уже обработанные операции. Сервер **обрабатывает каждую операцию в собственной транзакции** и не заявляет атомарность всей пачки. Для первого релиза клиент вправе отправлять строго **по одной операции** в запросе, и это предпочтительно до тестирования пакетной нагрузки. Ограничения: 1–50 операций, максимум 256 KiB JSON, проверка max string fields и nested depth.

**Конфликт:** текущая версия объекта отличается от `expectedVersion` → `CONFLICT` + только snapshot **данного** пользователя + actualVersion. Ни при каких условиях не делать silent last-write-wins. Чужой ID или отсутствующий собственный объект → одинаковый `NOT_FOUND` без чужого snapshot; конфликт уникальности логического ключа (например, два разных UUID бюджета за один месяц) → отдельный безопасный `CONFLICT` с принадлежащей пользователю канонической записью. Клиент должен иметь возможность явно разрешить конфликт.

**Идемпотентность:** ключ `(authenticatedUserId, operationId)`; в одной транзакции сравнить хеш **канонического нормализованного содержимого** запроса. Если ID и содержимое совпадают, вернуть ранее записанный результат, не повторяя финансовое изменение и не создавая sync-событие. Если ID тот же, но содержимое другое — `409 OPERATION_ID_REUSED`, без побочного эффекта. При корректной с точки зрения формы операции записывать итоговый детерминированный результат для повторов, включая конфликты/валидацию, по принятой схеме; исправленная операция получает **новый** `operationId`. Ошибочный синтаксис HTTP/JSON отклоняется до записи операции. Для устранения гонок **сериализовать операции одного пользователя**, например, `SELECT ... FOR UPDATE` строки `user_sync_state` до проверки idempotency/изменений. Не блокировать всех пользователей общей глобальной блокировкой.

**Важно:** response `ALREADY_APPLIED` должен давать достаточную информацию об исходном успешном результате (`entityVersion` и т. д.), чтобы клиент подтвердил собственный outbox. Уникальный `operationId` не должен использоваться как ключ поиска между пользователями.

### `GET /api/v1/sync/pull`

Пример:

```json
{
  "changes": [
    {
      "seq": 41,
      "entityType": "EXPENSE",
      "entityId": "019abc31-2200-7000-8000-000000000002",
      "operation": "UPSERT",
      "entityVersion": 1,
      "snapshot": {
        "id": "019abc31-2200-7000-8000-000000000002",
        "categoryId": "019abc31-3300-7000-8000-000000000003",
        "amountMinor": 12550,
        "occurredOn": "2026-10-31",
        "note": "Продукты"
      }
    }
  ],
  "nextCursor": 41,
  "hasMore": false
}
```

`cursor >= 0`, `1 <= limit <= 200`. `nextCursor` — sequence **последнего фактически выданного** события (если событий нет, прежний `cursor`), `changes` строго по `seq ASC`. Для `DELETE` отдавать tombstone (`entityType`, `entityId`, `entityVersion`, `operation=DELETE`, `snapshot=null`). `hasMore` вычислять по наличию следующих событий аккаунта. Курсор всегда **принадлежит логике текущего аккаунта**: без параметров `userId` и без возможности прочитать чужой журнал. Cursor больше текущего `last_seq` — явная валидационная ошибка, а не молчаливый пропуск истории.

**Правило распределения sequence:** не использовать `nextval()` глобального sequence для синхронизации: возможна ситуация, когда более раннее событие станет видимым позже события с большим seq. Внутри транзакции операции блокировать `user_sync_state` пользователя, увеличить `last_seq` и вставить `sync_changes(user_id, seq)` в **той же** транзакции. Порядок коммитов для одного аккаунта согласован с порядком sequence; разные аккаунты не блокируют друг друга. Получение `pull` — консистентное чтение страницы; курсор не должен перескочить за непрочитанное событие.

### Статусы и повторные запросы

- `400` / `422`: некорректное API-поле / payload; локальный клиент фиксирует ошибку, бесконечно не повторяет.
- `401`: невалидная/истёкшая сессия; Android пробует refresh, затем повтор с **тем же** `operationId`.
- `404` или `NOT_FOUND`: чужая либо отсутствующая сущность, без различимой детализации.
- `409`: `CONFLICT` / повтор `operationId` с другим содержимым.
- `429`: превышены лимиты; `Retry-After` и backoff.
- `5xx`, timeout, разрыв после commit: клиент повторяет **тот же** запрос, без двойного применения.

Не содержать `userId` клиента в DTO изменения. Никаких пагинационных `offset` в pull; только cursor.

## 9. Безопасность транспортного и серверного хранения

**TLS:** внешний API только HTTPS, TLS 1.2+ с предпочтением TLS 1.3, валидный сертификат, запрет HTTP для аутентификации и пользовательских данных, корректные timeouts и размеры запросов. Если TLS завершается reverse proxy, связь до сервера проходит по приватной изолированной сети; при удалённом размещении backend/БД — шифровать и внутренний канал. Использовать Caddy и доверенные proxy headers по разделу 7; `server.forward-headers-strategy` настроить явно, не доверять произвольному `X-Forwarded-*` из интернета. Не отключать валидацию сертификата на Android.

**Шифрование на сервере (at rest):** PostgreSQL располагается на шифрованном volume/disk провайдера или узла (полное шифрование блочного устройства), шифрованием защищаются snapshots и backup-файлы. Ключи хранятся отдельно от зашифрованных копий через инфраструктурный секрет-менеджер/KMS или эквивалентный защищённый механизм. Отдельно ограничить доступ DBA/infra, к SQL бэкапам и PostgreSQL. **TLS и шифрование диска не заменяют проверку владельца.** Backend законно видит расшифрованные записи при обработке; не заявлять сквозное E2E-шифрование, которого нет. Колонночное AES-GCM для `note` — **не требование MVP** и добавляется только после отдельного анализа угроз и поиска по полям, чтобы не дублировать криптографию.

**Пароли:** необратимые Argon2id-хеши в DelegatingPasswordEncoder, не AES; **access:** JWT HS256 с ключом ≥256 бит из файла-секрета и kid; **refresh/приглашения:** в БД только SHA-256-хеши случайных токенов/кодов. Утечки через логи недопустимы. Секреты только в runtime-env/secret manager/файлах-секретах; ключи JWT обязательно из файла-секрета, `.env.example` без реальных значений; production база не публикует порт в интернет. Сервер использует непривилегированного OS-пользователя; PostgreSQL runtime и миграционные роли раздельны.

**Backup/restore:** регулярные зашифрованные копии БД, документированная политика хранения, проверяемое восстановление в изолированный стенд. Backups обязаны сохранять `sync_changes`, `sync_operations`, версионность и `user_sync_state`, иначе клиентские курсоры могут стать некорректными. При откате БД на старый snapshot нужен **специальный план**: при потере уже подтверждённых сервером операций обычное восстановление без пересогласования клиентских курсоров недопустимо. До публичного релиза задокументировать handling recovery epoch/forced full resync или гарантировать восстановление без потери подтверждённых операций посредством согласованной стратегии. Не обещать нулевую потерю без соответствующей инфраструктуры.

**Защита от злоупотребления:** размер JSON, длина заметки/категории, ограничения диапазонов чисел, rate limiting авторизации, корректная обработка SQL injection (только параметризованный SQL), запрет подробных ошибок, не публиковать actuator endpoints кроме безопасного health. CORS для единственного Android-клиента не нужно открывать «*».

## 10. Алгоритмы и транзакционные границы, которые нужно реализовать

### 10.1 Регистрация

1. Валидировать inviteCode, email, пароль 12–128 по встроенному списку, валюту, deviceId и форму запроса.
2. Нормализовать email по зафиксированной политике; уникальность обеспечивает БД.
3. Проверить хеш/срок/неиспользованность приглашения; вычислить Argon2id вне долгой блокировки.
4. В одной DB transaction повторно проверить и заблокировать приглашение (FOR UPDATE), атомарно отметить used_at; конкурентно использовать один код может только один запрос.
5. Создать users со status=ACTIVE и email_verified_at=NULL, устройство без семьи сессии; установить RLS-контекст нового серверного UUID, создать user_sync_state и персональные категории.
6. Создать sync_changes категорий с упорядоченными seq и verify-токен; после commit поставить письмо в SMTP очередь. Вернуть 201 без токенов. Подтверждение email и последующий login обязательны.
7. При любой ошибке откатить всё, включая погашение приглашения; UNIQUE email не должен расходовать код при неудачной регистрации. Потеря успешного HTTP-ответа не разрешает повторное использование уже погашенного приглашения: клиент запрашивает повторное письмо, подтверждает email и входит с созданными учётными данными.

### 10.2 Применение одной `push`-операции

```text
validate authenticated principal and request shape
begin transaction
  set transaction-local app.current_user_id from verified principal
  lock current user's user_sync_state row (FOR UPDATE)
  find sync_operations(userId, operationId)
  if found:
    if canonicalRequestHash differs: report OPERATION_ID_REUSED
    else return previously recorded result, no mutation/no new seq
  else:
    validate entity ownership, business fields and expectedVersion
    if APPLIED:
      perform INSERT / UPDATE(version checked) / DELETE(version checked)
      increment user_sync_state.last_seq
      append UPSERT/tombstone to sync_changes with new seq
    persist deterministic result for this operationId
commit transaction
return result
```

Запись `sync_operations` должна хранить детерминированный безопасный ответ; при валидном синтаксисе конфликт не должен нарушать атомарность фиксации результата. Параметризованный SQL обязателен. При ошибке БД после любых частичных изменений транзакция откатывается целиком: клиент может повторить тот же `operationId`.

### 10.3 `pull` и взаимодействие с offline-клиентом

1. Из access-токена получить `userId`.
2. Открыть read-only транзакцию, установить RLS-контекст.
3. Получить `seq > cursor`, `ORDER BY seq`, ограничить страницу, определить `hasMore`.
4. Вернуть изменения только текущего аккаунта; не возвращать токены, hash пароля или чужие note.
5. На Android страница **и новый cursor сохраняются атомарно в одной Room-транзакции** (это требование к контракту клиента, не реализация данного backend).
6. При конфликтах Android не должен терять несинхронизированный локальный вариант. Сервер лишь отдаёт конфликт и актуальный серверный snapshot.

### 10.4 Административная команда create-invite

Локальная административная команда `create-invite` создаёт одноразовый код из **16 случайных байтов (128 бит)** и кодирует его base64url. TTL по умолчанию — **7 дней**, явный параметр `--ttl` задаёт положительный срок. Использовать CSPRNG и UTC-время; в БД записать только SHA-256-хеш, created_at, expires_at и пустой used_at. Исходный код вывести администратору однократно в результате команды после commit; исключить из обычных логов, telemetry и истории аргументов командной строки. Код не передаётся аргументом для создания.

Команда запускается только в доверенном административном окружении с отдельными ограниченными полномочиями выдачи приглашений; не выдавать runtime HTTP-процессу право создавать приглашения. Не предоставлять create-invite как публичный HTTP endpoint. Администратор передаёт код получателю вне приложения. Проверить права на команду, TTL по умолчанию/переопределение, отсутствие исходного кода в БД/логах и отказ на неверный TTL.

### 10.5 Опасные конкурентные случаи

- Две регистрации с одним приглашением → один аккаунт; другая регистрация не создаёт никаких данных.
- Отключение/удаление аккаунта одновременно с refresh → нельзя выдать действительную новую семью после отключения/удаления; порядок блокировок пользователя и семьи зафиксировать и протестировать.
- Два одновременных `CREATE` с одним `operationId` → один расход, одна запись результата, одно sync-событие.
- Два `UPDATE` на одной версии → первый успешно, второй `CONFLICT`, никакой silent overwrite.
- Одновременный refresh одной семьи → одна ротация; второй запрос с использованным токеном обнаруживает replay, коммитит отзыв всей семьи и возвращает 401. Новый токен первого запроса после этого также не действует; клиент сериализует refresh на устройстве.
- Добавление расхода через категорию другого аккаунта → отказ и отсутствие любых записей.
- Один аккаунт синхронизируется с двух устройств: оба получают всё через pull, без пропуска seq.
- Падение после DB commit до ответа HTTP → повтор той же операции возвращает исходный результат без второго действия.
- `CREATE` ещё в outbox, затем `UPDATE` того же объекта → клиент должен отправить их строго по очереди и для UPDATE взять подтверждённую серверную версию; сервер не подменяет незаполненную expectedVersion догадкой.

## 11. Стратегия автоматизированного тестирования

**Требование пользователя: минимальное покрытие тестами — 80%.** Определить измерение заранее и не менять порог ради зелёного CI.

### 11.1 Quality gate (обязателен)

1. **Общее покрытие строк (`LINE / COVEREDRATIO`) всего backend production bytecode — ≥ 80%**, включая Java и Kotlin. Тестовый код из знаменателя исключён естественным образом.
2. Дополнительно **≥ 80% line coverage** для критических областей `auth`, `security`, `sync`, `finance`, если они содержат production-логику. Для этого реализовать проверяемые отдельные JaCoCo rules/report по пакетам или отдельную проверку JaCoCo XML в CI; **нельзя** заменить требование только проверкой общего показателя.
3. **Branch coverage** также публиковать в отчёте и стремиться к ≥ 70% (рекомендация; обязательный минимум 80% относится к строкам). Для логики денег, безопасности и конфликта покрывать все существенные ветви независимо от процента.
4. Настроить **JaCoCo verification** так, чтобы `./gradlew clean check` или явно задокументированная команда CI **падала при 79.99%**, не просто печатала предупреждение.
5. Допустимые исключения: машинно сгенерированные классы/артефакты, которые физически не содержат пользовательской логики, и которые задокументированы с обоснованием. Нельзя исключать из метрики сервисы авторизации, security-фильтры, sync, контроллеры, репозитории, бизнес-валидацию ради достижения порога. Не добавлять бессмысленные тесты геттеров ради метрики.
6. **Все критические тесты обязательны**, даже если покрытие выше 80%. Тесты в CI должны выполняться на реальном контейнере PostgreSQL, а не только на H2/mocks. H2 не использовать как замену RLS/типам/блокировкам PostgreSQL.

Сдаваемые артефакты:
- HTML: `backend/build/reports/jacoco/test/html/index.html`;
- XML: `backend/build/reports/jacoco/test/jacocoTestReport.xml`;
- JUnit results: `backend/build/test-results/test/`;
- текстовый или машинно проверяемый список критических пакетов и их coverage;
- CI, в котором тесты и coverage обязательны для PR.

**Важно:** если unit и integration используют разные Gradle test tasks, **объединить данные покрытия до проверки**. Для простой первой реализации разрешается один `test` task, который выполняет и unit, и интеграционные тесты через JUnit 5 + Testcontainers; так проще получить однозначный coverage numerator/denominator.

### 11.2 Конфигурация JaCoCo в Gradle Kotlin DSL

В рабочем `build.gradle.kts` настрой версии плагинов, тестовые зависимости и toolchain. Минимальная схема **на одном task `test`**:

```kotlin
plugins {
    java
    jacoco
    id("org.springframework.boot") version "3.5.16"
    kotlin("jvm") version "2.4.21"
    kotlin("plugin.spring") version "2.4.21"
}

java {
    toolchain.languageVersion.set(JavaLanguageVersion.of(21))
}

kotlin {
    jvmToolchain(21)
}

tasks.test {
    useJUnitPlatform()
    finalizedBy(tasks.jacocoTestReport)
}

tasks.jacocoTestReport {
    dependsOn(tasks.test)
    reports {
        xml.required.set(true)
        html.required.set(true)
    }
}

tasks.jacocoTestCoverageVerification {
    dependsOn(tasks.test)
    violationRules {
        rule {
            element = "BUNDLE"
            limit {
                counter = "LINE"
                value = "COVEREDRATIO"
                minimum = "0.80".toBigDecimal()
            }
        }
    }
}

tasks.check {
    dependsOn(tasks.jacocoTestCoverageVerification)
    dependsOn(tasks.jacocoTestReport)
}
```

**Агент обязан дополнить этот пример** проверкой 80% для критических пакетов (`auth`, `security`, `sync`, `finance`) и проверить, что в собранном отчёте присутствуют одновременно `*.class` Java и Kotlin. Для отдельных пакетов пригодны JaCoCo rules с `element="PACKAGE"` и `includes`, либо отдельная проверка **XML JaCoCo**, учитывающая отсутствующие пакеты как ошибку конфигурации. Важно проверять агрегированное покрытие каждой бизнес-области со всеми её подпакетами, а не только головного пакета. Если используется отдельный скрипт, подключить его зависимостью к Gradle `check`, а также в CI. Не декларировать «80% для каждого пакета», не реализовав конкретную проверку. При изменениях проекта verify-контроль остаётся активен.

### 11.3 Пирамида тестов

| Уровень | Что проверяет | Инструменты |
|---|---|---|
| Unit | Денежные расчёты, валидация, expectedVersion, нормализация, маппинг ошибок | JUnit Jupiter, простые фейки/стабы |
| Integration DB | SQL, RLS, CHECK/FK/UNIQUE, миграции, транзакции, блокировки, `seq` | Testcontainers + **PostgreSQL 18** + JDBC |
| API/Security | 200/400/401/404/409/429, токены, чужие UUID, ошибки без утечек | Spring Boot Test + MockMvc / реальный HTTP |
| Concurrency/Failure | Два потока, обрыв ответа, повтор, конфликт, ротация токена, порядок событий | JUnit + Testcontainers + concurrency primitives |
| Smoke/Deployment | Старт контейнера, health, миграции, TLS, подключение к БД, backup restore | Docker Compose и CLI-проверки |

**Не мокать всё подряд.** Репозиторий и RLS проверяются с настоящей PostgreSQL. Моки/фейки использовать там, где они делают unit-тест быстрым и независимым; не проверять поведение мока вместо бизнес-результата. Тесты независимы от порядка запуска, не зависят от реальных SMTP, production API и интернета.

### 11.5 Надёжность, воспроизводимость и качество тестов

- В тестовом окружении создавать **двух разных пользователей** с независимыми категориями, бюджетами и расходами; использовать случайные UUID, а не захардкоженные общие IDs между тестами.
- Интеграционные тесты на PostgreSQL 18 запускаются с реальной runtime-ролью и RLS; миграции применяются штатным Flyway.
- Установка системных часов заменяется внедрённым `Clock`; не использовать `Thread.sleep` для ожидания гонок — использовать `CountDownLatch`, `CyclicBarrier` или управляемое событие.
- Конкурентные тесты проверяют **итог в БД + журнал + версии**, не только HTTP-код.
- Проверить падение транзакции `@Transactional` с реальным исключением; проверки должны видеть состояние **после** её окончания из другой транзакции.
- Для внешних компонентов (SMTP email) использовать fake/проверяемый adapter; не ходить в настоящие внешние сервисы.
- Отдельно контролировать отсутствие flaky-тестов: повтор запуска проблемного теста, стабильные timeouts, диагностические логи без секретов; никаких безусловных автоповторов падающих тестов в CI.
- Не использовать `assertDoesNotThrow()` как единственную проверку бизнес-сценария. Проверять реальные данные и отсутствие побочных эффектов.
- Запускать тесты в изоляции от production-секретов и production-DB.

## 12. CI/CD и команды проверки

### Минимальные локальные команды

Из `backend/`:

```bash
./gradlew clean test
./gradlew jacocoTestReport
./gradlew jacocoTestCoverageVerification
./gradlew clean check
./gradlew bootJar
```

`./gradlew clean check` **обязан** запускать unit+integration+security tests, создавать JaCoCo отчёт и проверять порог ≥80%; в противном случае пайплайн сконфигурирован неверно. Для integration с Testcontainers требуется работающий Docker; отсутствие Docker в CI = **ошибка сборки, не повод пропускать тесты**.

### GitHub Actions: обязательные шаги

1. Checkout исходников.
2. `actions/setup-java` с `distribution: temurin`, **`java-version: '21'`**.
3. Подготовить Gradle Wrapper, кеш Gradle, проверку wrapper checksum в соответствии с текущими рекомендациями.
4. Выполнить `cd backend && ./gradlew clean check bootJar --no-daemon` на Linux runner с доступным Docker для Testcontainers.
5. Опубликовать JUnit test results и JaCoCo HTML/XML как artifacts даже при падении (где это безопасно).
6. Fail job при ошибке теста, порога общего покрытия, любого критического пакета, миграции или запуска с PostgreSQL 18.
7. Не разворачивать production автоматически из непрошедшей проверки; deployment — отдельный защищённый job/окружение.
8. Не выводить production secrets, `.env` и тестовые токены в артефакты CI.

**Тест порога:** временно измените `minimum` на значение выше реально полученного покрытия и убедитесь, что CI падает, затем верните **0.80**. Это подтверждает, что gate не декоративный. Отдельно проверить включение Java и Kotlin классов в отчёт.

## 14. Дополнение 1.3: email и recovery epoch

Это дополнение заменяет прежнюю выдачу токенов при регистрации и дополняет sync API.
Регистрация возвращает 201 без тела/сессии. Login только ACTIVE с подтверждённым email.
POST /api/v1/auth/email/request и /password/forgot принимают email и дают одинаковый
202 ACCEPTED без раскрытия существования аккаунта. Cooldown 60 секунд на user/purpose;
общий IP rate limit сохраняется. Verify/reset: CSPRNG 256 бит/base64url, в БД SHA-256,
одноразовые, purpose-bound, TTL 24 часа/15 минут. Resend заменяет предыдущий токен.
POST /api/v1/auth/email/verify с token — 204; POST /api/v1/auth/password/reset с token,
password — 204, атомарно меняет пароль и отзывает все семьи/action tokens. Неверный,
использованный или истёкший токен — 400. Слабый пароль — 422 без погашения токена.

SMTP только после commit, bounded RAM-очередь и retry через resend при недоставке;
raw токены не сохраняются в БД/логах. В production обязательны AUTH/STARTTLS и проверка
сертификата. MAIL_PUBLIC_URL фиксирован; токен ссылки во fragment, GET не мутирует данные.
Клиентские страницы/Android и реальная доставляемость проверяются отдельно.

JWT добавляет обязательный claim ep. Все sync запросы, кроме GET /api/v1/sync/status,
требуют X-Recovery-Epoch; каждая outbox-операция имеет неизменяемый epoch при создании.
Отсутствие header — 428, устаревший epoch — 409 до idempotency/мутаций. Старые операции
не переназначаются новой эпохе. Backup исключает данные recovery_state/sync_recoveries;
после восстановления сервер создаёт новую epoch в RECOVERY, отзывает семьи/action tokens.
До административной активации API закрыт 503. Writers и prepare сериализованы advisory lock.

CLI recovery-prepare/status/activate использует отдельные migrator credentials; activate
требует --epoch UUID --reconciled после проверки данных и независимого реестра удалений.
После активации все устройства заново входят и проходят full replay: POST sync/recovery/start,
GET sync/recovery/{id}/pull от cursor=0 до cutoffSeq, POST sync/recovery/{id}/ack с lastCursor,
localCopyPreserved=true, pendingOperationsQuarantined=true. Без ack обычный push/pull запрещён.
Сеанс привязан к user/device/epoch, пропуск страниц запрещён, повтор страниц/ack разрешён.
Клиент сохраняет отдельную копию всех старых локальных данных (включая подтверждённые),
изолирует прежний outbox и сверяет потерянные действия; одобренные действия получают новые
operationId. Сервер проверяет доставку страниц и декларации, но не наличие локального файла.

V3 отзывает прежние сессии и требует подтверждения email старых аккаунтов. V4 требует
full replay всех устройств. Это несовместимое изменение протокола: старый клиент не
должен продолжать sync; необходим upgrade с сохранением старых данных. Восстановление
не реконструирует отсутствующие во всех копиях операции и не обещает RPO=0.
Контракт: backend/docs/openapi.yaml; процедуры: email-security.md и recovery-protocol.md.


## 15. Дополнение 1.4: статус создания и структура

Регистрация синхронно создаёт аккаунт и verify token, поэтому успех — 201 Created
без тела/сессии. Асинхронная доставка письма не меняет факт создания ресурса. Request/
resend/forgot сохраняют 202 ACCEPTED как принятую попытку отправки без раскрытия аккаунта.

Backend организован по слоям controller/service/repository/model. DTO — отдельные
файлы в model/dto, сущности SQL — model/entity с суффиксом Entity; ORM не добавляется.
Транзакции/проверки/бизнес-решения остаются в service, SQL в repository, JSON-маппинг
финансовых сущностей — mapper/finance. Конфигурация, security и admin отделены от слоёв.
Тесты unit и integration зеркалируют проверяемые слои, fixtures находятся в support.
Команды unitTest/integrationTest запускают отдельные группы; check по-прежнему проверяет
полный test, общий и четыре доменных порога >=80% с учётом всех новых путей классов.

Flyway имена V001__initial_schema.sql, V002__invites_jwt_families.sql,
V003__email_verification_and_reset.sql, V004__recovery_epochs.sql. SQL/версии/description
сохранены; ведущие нули не меняют версию Flyway. Проверить validate/migrate БД со старыми
именами без repair/history rewrite; не переименовывать применённые descriptions/SQL.


## 16. Дополнение 1.5: Spring DI и тесты

Spring Boot 3.5.16 / Spring Framework 6.2.19 сохраняют JUnit 5.13.4 и стандартные
@SpringBootTest/@WebMvcTest. Использовать constructor DI, @Configuration/@Bean,
@RequiredArgsConstructor и @Qualifier для нескольких инфраструктурных зависимостей.
Не создавать сервисные зависимости вручную. DTO/Entity — Lombok builders, секретные
поля не попадают в toString. Ручные вложенные типы вынести в отдельные файлы.

Unit-тесты используют Mockito с явными ожиданиями; Spring slice — только нужные
components и @MockitoBean. SQL/RLS проверять настоящей PostgreSQL; полный web context
оставить для HTTP/E2E/restore. Каждый тест именовать коротким русским @DisplayName.
WireMock нужен только при исходящих HTTP-интеграциях, которых сейчас нет.
Детальная архитектура и исключения для JDK/infrastructure создания — di-and-testing.md.

Требование к моделям: все DTO объявляются Java record, с Lombok @Builder;
конкретные DTO-классы с @Value/final class не используются. Обращение к полям через record-accessors.
